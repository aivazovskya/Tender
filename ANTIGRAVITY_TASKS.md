### P0-2. Playwright browser binaries отсутствуют в Docker-образе
`src/lib/ingestion/scraper.adapter.ts` использует `playwright` (fallback-скрапер для portal.sk.kz,
когда официальный API недоступен). `Dockerfile` (base: `node:20-alpine`) делает `npm ci`, но **не**
устанавливает браузерные бинарники Playwright (`npx playwright install`). На проде `ScraperAdapter`
будет падать при любой попытке скрапинга.
- Добавить в `Dockerfile` (стадия `deps` или `runner`) установку нужного браузера, например:
  `RUN npx playwright install --with-deps chromium`.
- Alpine накладывает дополнительные ограничения на системные зависимости Playwright/Chromium — при
  проблемах рассмотреть переход базового образа на `node:20-bookworm-slim` для стадии `runner`
  (там `playwright install --with-deps` работает надёжнее, чем на musl/alpine).
- Проверить итоговый размер образа — Chromium добавляет заметный вес; если ingestion воркер не должен
  тащить весь `web`-образ, стоит рассмотреть отдельный Dockerfile/target только для `worker`.

### P0-3. `vercel.json` cron-задачи не выполнятся в Docker Compose
Репозиторий содержит `vercel.json` с 4 cron-маршрутами (`/api/cron/health-check`,
`/api/notifications/check-security-expiry`, `/api/cron/check-upcoming-deadlines`,
`/api/cron/check-submitted-tender-results`). **Vercel Cron работает только на самой платформе Vercel.**

### P0-4. `docker-compose.yml`: `db`/`redis` смотрят наружу без ограничений
```yaml
db:
  ports:
    - "5432:5432"
redis:
  ports:
    - "6379:6379"
```
На публичном VPS это открывает Postgres и Redis всему интернету на дефолтных портах. Внутри
Compose-сети `web`/`worker`/`bot` и так достучатся до `db:5432` / `redis:6379` по имени сервиса —
внешний проброс портов не нужен для работы приложения.
- Убрать секции `ports` у `db` и `redis` (оставить сервисы только во внутренней docker-сети), либо,
  если нужен внешний доступ для отладки, забиндить на `127.0.0.1:5432:5432` и защищать firewall'ом
  (ufw/security group), не оставлять `0.0.0.0`.

### 7.2. Что предлагается добавить (MVP)

Цель: сгенерированный документ реально отвечает на требования конкретного лота, а не только шапку с
реквизитами.

1. **Новый тип шаблона — «Техническая часть заявки» / «Форма соответствия требованиям»** (отдельно от
   существующих доверенности/гарантийного письма, их не трогать). Тело шаблона должно поддерживать
   вставку динамического раздела (не просто плейсхолдер-строку, а список), а не только 7 старых плейсхолдеров.
2. **Раздел "Подтверждение соответствия требованиям"** — генерируется из `TenderRequirementItem[]` лота:
   каждый пункт чек-листа (с приоритетом на отмеченные `isCompleted: true`) выводится строкой в документе
   с местом для ответа компании ("соответствует/не соответствует", комментарий). Источник данных уже есть
   (`GET /api/tenders/{id}/requirements`), просто раньше не использовался при генерации.
3. **Данные себестоимости** — если у лота есть `TenderCalculation` с позициями (`TenderCostItem`), опционально
   добавить итоговую сумму КП в документ (не переносить всю смету, просто финальную цифру и валюту).
4. Точка входа — расширить `POST /api/tenders/[id]/documents/generate`, принимать `templateId` нового типа
   и подтягивать чек-лист/расчёт в `resolvePlaceholders`-подобную функцию (скорее всего понадобится
   заменить простую подстановку строк на построение документа посекционно, раз данных больше не 7 скаляров).

### 7.3. Осознанно вне MVP (не делать сразу)

- Повторное/ленивое извлечение текста документа по требованию пользователя (сейчас только при инжесте) —
  отдельная, самостоятельная задача, если понадобится.
- Переход RAG-чата на честный чанкинг/векторный поиск вместо context stuffing — не блокирует эту фичу,
  текущий подход достаточен для документов в разумный размер (до ~10 000 симв.).
- Категорийные шаблоны (отдельно для ИТ/строительства/услуг) — начать с одного универсального шаблона,
  расширять по факту использования.

### 7.4. Решения (владелец продукта делегировал архитектору, зафиксировано 2026-09-16)

1. **Экспорт — сразу настоящий `.docx`, не промежуточный текстовый MVP.** Механизм
   `DocGeneratorService.generateDocxBuffer` уже реализован и используется для двух существующих
   шаблонов — расширение на новый тип шаблона дешевле, чем городить отдельную "облегчённую" версию,
   которую всё равно пришлось бы потом доводить до реального файла.
2. **Не ждём образец формы.** Формат — по аналогии с двумя существующими шаблонами: официальное письмо
   с шапкой реквизитов (компания/БИН/лот/заказчик), затем нумерованный список пунктов из чек-листа
   `TenderRequirementItem[]` с местом под "соответствует/не соответствует" и комментарий. Это
   консервативный, безопасный дефолт — если у владельца продукта позже появится реальный образец из
   практики казахстанских госзакупок, перевёрстка под него — не архитектурное изменение, а правка
   одного шаблона.
