## 5. Функциональный аудит: найденные баги (2026-09-15)

Проведён параллельный аудит всей кодовой базы по 6 подсистемам (auth/RBAC, billing/Kaspi/Telegram,
ingestion/cron, core tender API, kanban/export/finance, frontend↔API контракты). Ниже — подтверждённые
находки, отсортированные по критичности. `[CONFIRMED]` — лично перепроверено чтением кода;
`[PLAUSIBLE]` — найдено субагентом с конкретными file:line, не перепроверено лично, но с высокой
уверенностью. **Это блокеры P0 для деплоя** — часть из них означает, что ключевые платные функции
(оплата, агрегация тендеров) не будут работать в проде вообще, а не просто "с багами".

### 5.1. Критично — ломает основной функционал в проде

1. **`[CONFIRMED]` `src/middleware.ts:28`** — глобальный auth-гейт не исключает
   `/api/billing/kaspi/webhook` и `/api/telegram/webhook`. Реальные вызовы от Kaspi/Telegram (без
   session cookie/API-ключа) получают `401` от middleware **до** того, как роут успевает проверить
   HMAC-подпись. **Следствие: ни один платёж через Kaspi Pay не может подтвердиться в проде** —
   подписка никогда не активируется. Фикс: добавить точное совпадение этих двух путей в allow-list
   (аналогично `pathname.startsWith('/api/cron/')` на строке 28), пропуская их до общей auth-проверки,
   поскольку у них есть собственная проверка подписи внутри роута.

2. **`[CONFIRMED]` `src/lib/ingestion/goszakup.adapter.ts:16`** и
   **`[PLAUSIBLE]` `src/lib/ingestion/samruk.adapter.ts:14`** — запросы к обоим источникам жёстко
   ограничены `limit: 10` без `offset`/курсора/цикла. **Следствие: если между двумя плановыми
   синками на источнике опубликовано больше 10 новых лотов, лишние лоты не попадают в систему
   никогда** (не переспрашиваются на следующем прогоне, так как "топ-10 новых" на момент N+1 уже не
   содержит их). Это ядро модуля агрегации (Module 1 из README) — тихая потеря данных без ошибок в
   логах. Фикс: реализовать постраничный обход (offset/cursor) до исчерпания источника или до
   заданного разумного потолка на один прогон.

3. **`[CONFIRMED]` `src/app/page.tsx:255`** — главная страница не отправляет `page`/`limit` в
   `/api/tenders` и просто делает `setTenders(data.tenders)`, игнорируя `total`/`totalPages`. С тех
   пор как бэкенд стал возвращать постранично (по умолчанию 20 записей), **фронтенд молча показывает
   максимум 20 тендеров из всей базы**, без какого-либо UI для остальных страниц. Ломает: счётчик
   "Найдено тендеров", клиентскую фильтрацию по сумме (может показать "ничего не найдено" при
   реальных совпадениях на 2+ странице), ИИ-матчинг по профилю компании (видит только 20 последних
   тендеров), полнотекстовый поиск. Фикс: добавить пагинацию в `page.tsx` (курсор/номер страницы +
   контролы "далее"/infinite scroll) и синхронизировать со серверной пагинацией `/api/tenders`.

### 5.2. Критично — утечка данных между тенантами (cross-tenant leak)

4. **`[CONFIRMED]` `src/app/api/export/kanban/route.ts:33`** — `prisma.kanbanCard.findMany` вообще
   без `where`, в отличие от `GET /api/kanban`, где фильтр по `userId` есть. Экспорт Kanban в Excel
   отдаёт воронку **всех** компаний платформы (ответственные, заметки, суммы сделок) любому
   пользователю, у которого достаточно тарифа для экспорта.

5. **`[CONFIRMED]` `src/app/api/tenders/[id]/documents/route.ts:9`** — результат `validateApiAuth()`
   вычисляется, но никогда не проверяется, запрос к `generatedDocument` без привязки к компании.
   Любой аутентифицированный пользователь видит сгенерированные документы **любой** компании по
   конкретному тендеру, включая `companyName`/`bin` конкурентов.

6. **`[PLAUSIBLE]` `src/app/api/tenders/[id]/supplier-comparison/route.ts:9`** (+ `export-excel`) —
   `auth.authorized` не проверяется, и при отсутствии профиля компании сервис (`supplier-comparison.service.ts:163-167`)
   откатывается на запрос без фильтра по `companyId`. Может отдать закупочные цены и маржу конкурента.

7. **`[PLAUSIBLE]` `src/app/api/security-instruments/[id]/route.ts:9`** — `PATCH` не проверяет
   принадлежность инструмента компании вызывающего (в отличие от `GET`/`POST` того же модуля) — IDOR,
   позволяет менять чужие банковские гарантии/обеспечения по угадываемому ID.

8. **`[PLAUSIBLE]` `src/app/api/reports/management/route.ts:48`** — `ManagementReportService.generateReport`
   вызывается без scope по организации, агрегирует данные **всех** организаций платформы вместо
   организации вызывающего.

### 5.3. Важно — платежи и уведомления

9. **`[CONFIRMED]` `src/app/api/billing/kaspi/create-order/route.ts:7`** — `auth.authorized` не
   проверяется (в отличие от `change-plan`/`grant-plan`). Пользователь со статусом `PENDING`/`REJECTED`
   всё равно может создать реальный оплачиваемый заказ.

10. **`[PLAUSIBLE]` `src/app/api/billing/kaspi/webhook/route.ts:161`** — активация подписки по полю
    `bin` из тела вебхука не сверяется с фактическим владельцем заказа (`existingPayment.userId`/
    `organizationId`). Если это поле в реальном платеже Kaspi может не совпадать с инициатором заказа
    (общие/корпоративные Kaspi-счета) — подписка может активироваться не на той компании. Нужна сверка
    с продуктовой/платёжной командой, как Kaspi реально формирует это поле, прежде чем чинить.

11. **`[PLAUSIBLE]` `src/app/api/notifications/recompute-stats/route.ts:13`** — при
    `NODE_ENV !== 'production'` (в точности) и отсутствии заголовка секрета авторизация проходит
    безусловно — в отличие от двух других cron-роутов, требующих точного совпадения секрета всегда.

12. **`[PLAUSIBLE]` `src/lib/telegram/bot.service.ts:106`** — сравнение HMAC-подписи deep-link через
    `!==` вместо `crypto.timingSafeEqual` (который уже используется в Kaspi-вебхуке), плюс отсутствие
    защиты от повторного использования токена в течение 15-минутного TTL.

### 5.4. Второстепенное (не блокирует деплой, но стоит закрыть)

13. **`[PLAUSIBLE]` `src/lib/security/ssrf.ts:107`** — `net.isIP()` не распознаёт IP в decimal/hex/
    octal-нотации, поэтому `validateUrlForSSRF` можно обойти на админских эндпоинтах
    scraper-config (`http://2130706433/...` вместо `127.0.0.1`).
14. **`[PLAUSIBLE]` `src/lib/security/auth.ts:55`** — сравнение `ADMIN_API_KEY` через `===` вместо
    `crypto.timingSafeEqual`, непоследовательно с остальным кодом.
15. Доп. находки меньшей значимости из аудита (не включены выше, см. полный список у ревьюера при
    необходимости): дублирование `TenderRequirementItem` при гонке двух параллельных первых запросов
    (`requirements/route.ts`), просроченные дедлайны показывают `daysRemaining: 0` вместо
    "просрочено" (`deadline.service.ts:268-271`), дедупликация уведомлений по UTC-дате вместо
    времени Алматы (двойные уведомления в окне 00:00–05:00 по Алматы), GraphQL-инъекция через
    неэкранированный `externalId` в `fetchBuyResult`, `fetchBuyResult` не использует общий

## 0. Контекст

TenderAI — Next.js 14 App Router монолит + отдельный BullMQ-воркер (`scripts/ingestion-worker.js`) +
отдельный Telegram-бот (`scripts/telegram-bot.js`), PostgreSQL, Redis. Целевой способ деплоя,
выбранный владельцем — **Docker Compose на собственном VPS** (не Vercel), хотя в репозитории
присутствует `vercel.json` — это важно, см. P0-4 ниже.

Проверено на текущий момент (`git log -1`: `a5f0acf` на `main`, ещё не запушен в origin):
- `npm run build` — проходит чисто (51 route, standalone output).
- `npm run check:client-secrets` — проходит.
- 40 из 47 тест-сьютов (`npm test`) проходят локально без БД; оставшиеся 7 виснут локально
  только из-за отсутствия Postgres/Redis на машине анализа (Docker недоступен там) — не признак
  реальных багов, но и не подтверждены.
- Функционально не нашли TODO/заглушек/недописанных модулей при грепе `src/` — все 9 модулей
  из README на вид реализованы.

## 1. Уже сделано (не переделывать)

**Коммит `a5f0acf`** (локально, не запушен) — `fix(ci): stop forcing ALLOW_DEMO_AUTH=true on the whole test job`.

Причина: CI (`.github/workflows/ci.yml`) 10 прогонов подряд (#40–#49, все текущие на `main`) были
красными. Root cause: workflow жёстко ставил `ALLOW_DEMO_AUTH: 'true'` на весь шаг `npm test`, а тесты
`deadline-tracker.test.js` и `review-defects-fixes.test.js` написаны в расчёте на то, что флаг по
умолчанию выключен (сами переключают его по ходу теста, чтобы проверить оба режима — защищённый и
demo). С глобальным `true` неаутентифицированные запросы в этих двух сьютах вместо `401` получали
`200`/`404` (demo-user-id молча авторизовывался). Подтверждено двумя прогонами полного набора тестов
локально (до/после фикса — оба ранее падавших сьюта после фикса проходят).

`ALLOW_DEMO_AUTH` как фича — это осознанное поведение (публичный demo-доступ без логина), не дыра:
`auth-audit-critical-fixes.test.js` явно тестирует, что оно должно работать и в NODE_ENV=production,
когда флаг явно включён оператором. **Не трогать `src/lib/security/auth.ts` из-за этого.**

## 2. Задачи (P0 — блокеры перед деплоем)

### P0-1. Запушить и подтвердить зелёный CI
- `git push origin main` (коммит `a5f0acf` уже в локальном `main`, push не прошёл из окружения анализа
  из-за отсутствия интерактивной авторизации git — обычный `git push` должен отработать у исполнителя).
- Дождаться прогона `CI Pipeline` на GitHub Actions, убедиться, что все 47 сьютов зелёные — включая
  7 сьютов, не проверенных локально: `competition-estimate`, `customer-analytics`, `deadline-tracker`,
  `export-reports`, `public-api-keys`, `reputation-check`, `roadmap-phase-3-audit-fixes`.
- Если что-то из этих 7 всё же красное в реальном CI (с настоящими Postgres/Redis) — разобрать отдельно,
  это не будет тем же багом, что уже пофикшен.

### P0-2. Playwright browser binaries отсутствуют в Docker-образе
`src/lib/ingestion/scraper.adapter.ts` использует `playwright` (fallback-скрапер для portal.sk.kz,
когда официальный API недоступен). `Dockerfile` (base: `node:20-alpine`) делает `npm ci`, но **не**
устанавливает браузерные бинарники Playwright (`npx playwright install`). На проде `ScraperAdapter`
будет падать при любой попытке скрапинга.
- Добавить в `Dockerfile` (стадия `deps` или `runner`) установку нужного браузера, например:
  `RUN npx playwright install --with-deps chromium`.
- Alpine накладывает дополнительные ограничения на системные зависимости Playwright/Chromium — при
  проблемах рассмотреть переход базового образа на `node:20-bookworm-slim` для стадии `runner`
  (там `playwright install --with-deps` работает надёжнее, чем на musl/alpine).
- Проверить итоговый размер образа — Chromium добавляет заметный вес; если ingestion воркер не должен
  тащить весь `web`-образ, стоит рассмотреть отдельный Dockerfile/target только для `worker`.

### P0-3. `vercel.json` cron-задачи не выполнятся в Docker Compose
Репозиторий содержит `vercel.json` с 4 cron-маршрутами (`/api/cron/health-check`,
`/api/notifications/check-security-expiry`, `/api/cron/check-upcoming-deadlines`,
`/api/cron/check-submitted-tender-results`). **Vercel Cron работает только на самой платформе Vercel.**
При деплое через Docker Compose эти эндпоинты никогда не будут вызваны — часть функциональности
(дедлайны, уведомления, проверка результатов) тихо перестанет работать.
- Добавить свой планировщик под self-host: либо системный `crontab` на VPS с `curl` + заголовком
  `X-Cron-Secret: $CRON_SECRET` на каждый из 4 эндпоинтов с расписанием, зеркальным `vercel.json`
  (`0 * * * *`, `0 8 * * *`, `0 7,19 * * *`, `0 6,18 * * *`), либо лёгкий 5-й контейнер
  (например `node-cron`/`supercronic`) в `docker-compose.yml`.
- `CRON_SECRET` должен быть задан в `.env` и совпадать с тем, что ждут `/api/cron/*` роуты
  (проверить `src/app/api/cron/*/route.ts` на используемое имя заголовка/env-переменной).

### P0-4. `docker-compose.yml`: `db`/`redis` смотрят наружу без ограничений
```yaml
db:
  ports:
    - "5432:5432"
redis:
  ports:
    - "6379:6379"
```
На публичном VPS это открывает Postgres и Redis всему интернету на дефолтных портах. Внутри
Compose-сети `web`/`worker`/`bot` и так достучатся до `db:5432` / `redis:6379` по имени сервиса —
внешний проброс портов не нужен для работы приложения.
- Убрать секции `ports` у `db` и `redis` (оставить сервисы только во внутренней docker-сети), либо,
  если нужен внешний доступ для отладки, забиндить на `127.0.0.1:5432:5432` и защищать firewall'ом
  (ufw/security group), не оставлять `0.0.0.0`.

### P0-5. Продакшн `.env` — заполнить реальными секретами
На основе `.env.example`, обязательные для полноценной работы (не заглушки):
- `DATABASE_URL`, `POSTGRES_PASSWORD` — реальный пароль (не `change_me_before_deploy`).
- `REDIS_URL` — оставить `redis://redis:6379` (имя сервиса в Compose-сети), см. P0-4.
- `KASPI_WEBHOOK_SECRET`, `KASPI_PAY_MERCHANT_ID` — из мерчант-кабинета Kaspi Pay.
- `TELEGRAM_BOT_TOKEN` — от @BotFather.
- `GOSZAKUP_API_TOKEN`, `SAMRUK_API_TOKEN` — персональные токены участника закупок (иначе адаптеры
  идут в graceful fallback на демо-данные — сверить, устраивает ли это на старте).
- `LLM_API_KEY` (Gemini) — для ИИ-резюме/риск-оценки/чат-бота по лоту.
- `ADMIN_API_KEY` — задать нетривиальное значение (в dev сейчас `dev-admin-key` — не переносить в прод).
- `CRON_SECRET`, `JWT_SECRET` — сгенерировать новые случайные секреты для прода, не использовать
  `ci-test-*` значения из CI.
- **`ALLOW_DEMO_AUTH`** — явное решение владельца продукта: если прод должен требовать логин у всех —
  **не задавать** эту переменную вообще (или `false`). Если нужен публичный demo-режим без логина —
  осознанно выставить `true`, понимая, что это даёт анонимный доступ к части API под `demo-user-id`
  (см. секцию 1 выше — поведение протестировано и является фичей, а не багом).

### P0-6. Провизия VPS и первичный запуск
- Docker + Docker Compose на сервере (минимум ~2 vCPU / 4 GB RAM на 5 контейнеров: web, worker, bot,
  postgres, redis).
- Reverse proxy с TLS перед `web` (Compose не включает nginx/caddy) — нужен домен + сертификат
  (Let's Encrypt), проксирующий `:443` → `tender_web:3000`.
- `git clone`, `cp .env.example .env` → заполнить (см. P0-5), `docker compose up --build -d`.
- `npx prisma db push` (или подготовить `prisma migrate deploy`, если хотим версионируемые миграции
  вместо `db push` — сейчас в README используется `db push`, что нормально для старта, но стоит решить,
  переходить ли на `prisma migrate` для управляемости схемы в проде).
- `npm run seed` — только если нужны демо-данные на старте; для чистого прод-окружения решить, нужен
  ли сид вообще (сейчас сид явно упомянут в README как обязательный шаг — уточнить у владельца).
