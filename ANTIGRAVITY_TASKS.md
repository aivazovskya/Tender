### 5.1. Критично — ломает основной функционал в проде

1. **`[CONFIRMED]` `src/middleware.ts:28`** — глобальный auth-гейт не исключает
   `/api/billing/kaspi/webhook` и `/api/telegram/webhook`. Реальные вызовы от Kaspi/Telegram (без
   session cookie/API-ключа) получают `401` от middleware **до** того, как роут успевает проверить
   HMAC-подпись. **Следствие: ни один платёж через Kaspi Pay не может подтвердиться в проде** —
   подписка никогда не активируется. (Примечание: Telegram-бот у нас работает в режиме long polling
   — `bot.launch()` в `scripts/telegram-bot.ts` — так что `/api/telegram/webhook` сейчас, похоже,
   вообще не используется штатным ботом; но баг в middleware всё равно нужно чинить хотя бы ради
   Kaspi, и `/api/telegram/webhook` стоит явно исключить на будущее.) Фикс: добавить точное совпадение
   `/api/billing/kaspi/webhook` (и `/api/telegram/webhook`) в allow-list рядом со строкой 28, пропуская
   их до общей auth-проверки, поскольку у них есть собственная проверка подписи внутри роута.

2. **`[CONFIRMED]` `src/app/page.tsx:255`** — главная страница не отправляет `page`/`limit` в
   `/api/tenders` и просто делает `setTenders(data.tenders)`, игнорируя `total`/`totalPages`. С тех
   пор как бэкенд стал возвращать постранично (по умолчанию 20 записей), **фронтенд молча показывает
   максимум 20 тендеров из всей базы**, без какого-либо UI для остальных страниц. Ломает: счётчик
   "Найдено тендеров", клиентскую фильтрацию по сумме (может показать "ничего не найдено" при
   реальных совпадениях на 2+ странице), ИИ-матчинг по профилю компании (видит только 20 последних
   тендеров), полнотекстовый поиск. Фикс: добавить пагинацию в `page.tsx` (курсор/номер страницы +
   контролы "далее"/infinite scroll) и синхронизировать со серверной пагинацией `/api/tenders`.

## 2. Задачи (P0 — блокеры перед деплоем)

### P0-1. Запушить и подтвердить зелёный CI
- `git push origin main` (коммит `a5f0acf` уже в локальном `main`, push не прошёл из окружения анализа
  из-за отсутствия интерактивной авторизации git — обычный `git push` должен отработать у исполнителя).
- Дождаться прогона `CI Pipeline` на GitHub Actions, убедиться, что все 47 сьютов зелёные — включая
  7 сьютов, не проверенных локально: `competition-estimate`, `customer-analytics`, `deadline-tracker`,
  `export-reports`, `public-api-keys`, `reputation-check`, `roadmap-phase-3-audit-fixes`.
- Если что-то из этих 7 всё же красное в реальном CI (с настоящими Postgres/Redis) — разобрать отдельно,
  это не будет тем же багом, что уже пофикшен.

### P0-2. Playwright browser binaries отсутствуют в Docker-образе
`src/lib/ingestion/scraper.adapter.ts` использует `playwright` (fallback-скрапер для portal.sk.kz,
когда официальный API недоступен). `Dockerfile` (base: `node:20-alpine`) делает `npm ci`, но **не**
устанавливает браузерные бинарники Playwright (`npx playwright install`). На проде `ScraperAdapter`
будет падать при любой попытке скрапинга.
- Добавить в `Dockerfile` (стадия `deps` или `runner`) установку нужного браузера, например:
  `RUN npx playwright install --with-deps chromium`.
- Alpine накладывает дополнительные ограничения на системные зависимости Playwright/Chromium — при
  проблемах рассмотреть переход базового образа на `node:20-bookworm-slim` для стадии `runner`
  (там `playwright install --with-deps` работает надёжнее, чем на musl/alpine).
- Проверить итоговый размер образа — Chromium добавляет заметный вес; если ingestion воркер не должен
  тащить весь `web`-образ, стоит рассмотреть отдельный Dockerfile/target только для `worker`.

### P0-3. `vercel.json` cron-задачи не выполнятся в Docker Compose
Репозиторий содержит `vercel.json` с 4 cron-маршрутами (`/api/cron/health-check`,
`/api/notifications/check-security-expiry`, `/api/cron/check-upcoming-deadlines`,
`/api/cron/check-submitted-tender-results`). **Vercel Cron работает только на самой платформе Vercel.**
При деплое через Docker Compose эти эндпоинты никогда не будут вызваны — часть функциональности
(дедлайны, уведомления, проверка результатов) тихо перестанет работать.
- Добавить свой планировщик под self-host: либо системный `crontab` на VPS с `curl` + заголовком
  `X-Cron-Secret: $CRON_SECRET` на каждый из 4 эндпоинтов с расписанием, зеркальным `vercel.json`
  (`0 * * * *`, `0 8 * * *`, `0 7,19 * * *`, `0 6,18 * * *`), либо лёгкий 5-й контейнер
  (например `node-cron`/`supercronic`) в `docker-compose.yml`.
- `CRON_SECRET` должен быть задан в `.env` и совпадать с тем, что ждут `/api/cron/*` роуты
  (проверить `src/app/api/cron/*/route.ts` на используемое имя заголовка/env-переменной).

### P0-4. `docker-compose.yml`: `db`/`redis` смотрят наружу без ограничений
```yaml
db:
  ports:
    - "5432:5432"
redis:
  ports:
    - "6379:6379"
```
На публичном VPS это открывает Postgres и Redis всему интернету на дефолтных портах. Внутри
Compose-сети `web`/`worker`/`bot` и так достучатся до `db:5432` / `redis:6379` по имени сервиса —
внешний проброс портов не нужен для работы приложения.
- Убрать секции `ports` у `db` и `redis` (оставить сервисы только во внутренней docker-сети), либо,
  если нужен внешний доступ для отладки, забиндить на `127.0.0.1:5432:5432` и защищать firewall'ом
  (ufw/security group), не оставлять `0.0.0.0`.

### P0-5. Продакшн `.env` — заполнить реальными секретами
На основе `.env.example`, обязательные для полноценной работы (не заглушки):
- `DATABASE_URL`, `POSTGRES_PASSWORD` — реальный пароль (не `change_me_before_deploy`).
- `REDIS_URL` — оставить `redis://redis:6379` (имя сервиса в Compose-сети), см. P0-4.
- `KASPI_WEBHOOK_SECRET`, `KASPI_PAY_MERCHANT_ID` — из мерчант-кабинета Kaspi Pay.
- `TELEGRAM_BOT_TOKEN` — от @BotFather.
- `GOSZAKUP_API_TOKEN`, `SAMRUK_API_TOKEN` — персональные токены участника закупок (иначе адаптеры
  идут в graceful fallback на демо-данные — сверить, устраивает ли это на старте).
- `LLM_API_KEY` (Gemini) — для ИИ-резюме/риск-оценки/чат-бота по лоту.
- `ADMIN_API_KEY` — задать нетривиальное значение (в dev сейчас `dev-admin-key` — не переносить в прод).
- `CRON_SECRET`, `JWT_SECRET` — сгенерировать новые случайные секреты для прода, не использовать
  `ci-test-*` значения из CI.
- **`ALLOW_DEMO_AUTH`** — явное решение владельца продукта: если прод должен требовать логин у всех —
  **не задавать** эту переменную вообще (или `false`). Если нужен публичный demo-режим без логина —
  осознанно выставить `true`, понимая, что это даёт анонимный доступ к части API под `demo-user-id`
  (см. секцию 1 выше — поведение протестировано и является фичей, а не багом).

### P0-6. Провизия VPS и первичный запуск
- Docker + Docker Compose на сервере (минимум ~2 vCPU / 4 GB RAM на 5 контейнеров: web, worker, bot,
  postgres, redis).
